## 1. Обзор продукта

**CopyTrading** — ASP.NET Core 8.0 приложение для автоматического копирования торговых позиций отслеживаемых криптовалютных кошельков на бирже HyperLiquid. Система в реальном времени получает ордера и сделки трейдеров через WebSocket, определяет тип операции (Open/Increase/Decrease/Close), пропорционально масштабирует объём позиции под баланс собственного счёта и размещает зеркальные ордера на бирже.

### Целевой пользователь
Один пользователь (владелец `MyWallet`), который хочет автоматически повторять сделки выбранных трейдеров с сохранением пропорции риска.

## 3. Архитектура системы

### 3.1 Поток данных

```
HyperLiquid Exchange (WebSocket)
        ↓
OrdersTradesSubscriber
        ↓ публикует
DataBusEvents.NewOrders / NewTrades
        ↓ подписан единственный
OrderService (медиатор)          TradeService (медиатор)
    ↓ вызывает методы                ↓ вызывает методы
    ├─ CurrentWalletPositionService   ├─ FillsOrderService
    ├─ FillsOrderService             ├─ CurrentWalletPositionService
    ├─ RealtimeUpdateService          └─ RealtimeUpdateService
    └─ CopyOrderService2
              ↓
        OrdersProvider (HyperLiquid API)
              ↓
        [размещение ордеров на бирже]
```

### 3.2 Хранилища данных

| Хранилище | Назначение | Статус |
|-----------|-----------|--------|
| **Redis** | Hot-cache ордеров (`FillsOrderService`) | Основное |
| **SQLite / SQLliteBD** | Текущее локальное персистентное хранилище | Подлежит выводу из использования |
| **InfluxDB** | Time-series аналитика (ордера, сделки, свечи) | Аналитика |
| **PostgreSQL** | Legacy — выводится из использования | Deprecated |

### 3.3 Ключевые сервисы и их жизненный цикл

Все ключевые сервисы — **Singleton**. Часть из них требует явной активации в `Startup.Configure()` для регистрации подписок на события:

```

serviceProvider.GetService<OrderService>()
serviceProvider.GetService<FillsOrderService>()
serviceProvider.GetService<CopyOrderService>() → ICopyOrderService = CopyOrderService2
serviceProvider.GetRequiredService<CopyOrderStorageService>()
serviceProvider.GetRequiredService<RealtimeUpdateService>()
```

## 4. Бизнес-логика

### 4.1 Расчёт объёма копируемого ордера

```
orderRatio      = order.VolumeUsd / traderAccountVolume
myVolumeUsd     = myAccountVolume × orderRatio
myQuantity      = myVolumeUsd / order.Price
myQuantity      = Round(myQuantity, exchangeInfo.QuantityDecimals)
```

**Проверки перед размещением:**
- `myVolumeUsd >= MinNotionalValue` ($10)
- `myQuantity >= MinTradeQuantity`

### 4.2 Расчёт OrderSubType (двухэтапный)

**Этап 1** (для каждого нового ордера до добавления в `FillsOrderService`):
- Учитываются только ордера с OrderId < текущего
- Исключает взаимовлияние ордеров из одного batch

**Этап 2** (пересчёт после добавления всех ордеров):
- Группировка по `(Wallet, Symbol)`
- Пересчёт SubType для всех pending ордеров
- Обновление через `FillsOrderService.UpdateOrderSubType()`

### 4.3 Логика копирования по SubType

| SubType | Маппинг есть | Маппинга нет |
|---------|-------------|--------------|
| **Open** | Ошибка (уже есть позиция) | Открываем новую позицию |
| **Increase** | Увеличиваем по сохранённому PositionRatio | **Умная синхронизация**: берём всю текущую позицию трейдера из snapshot |
| **Decrease** | Уменьшаем по доле относительно baseline | Не копируем, логируем |
| **Close** | Закрываем всю нашу позицию | Не копируем, логируем |

### 4.4 Концепция Baseline (TraderQuantityAtEntry)

При открытии позиции сохраняется **базовая линия** — позиция трейдера ДО нашего входа:
- Open → `TraderQuantityAtEntry = 0`
- Increase (умная синхронизация) → `TraderQuantityAtEntry = traderTotalQuantity - order.Quantity`

При Decrease:
- Если `actualTraderQuantity <= TraderQuantityAtEntry` → закрываем ВСЁ
- Иначе → `closeRatio = order.Quantity / (actualTraderQuantity - TraderQuantityAtEntry)`

### 4.5 Источник истины для позиции трейдера

**Snapshot** (`CurrentWalletPositionService`) — единственный источник истины для реальной позиции трейдера. `mapping.TraderQuantity` НЕ используется для расчётов (только для отладки/логирования). Snapshot обновляется через трейды (реальные исполнения), что автоматически учитывает комиссии, проскальзывание, частичное исполнение.

## 6. Требования к реализации (Backlog)

### 6.1 P0 — Критично для работы в production

#### [P0-1] Реальное размещение ордеров на бирже
**Задача:** Реализовать `OrdersProvider` методы для реального взаимодействия с HyperLiquid API.

Необходимые методы:
- `PlaceOrder(symbol, direction, quantity, price, leverage, orderType)`
- `CancelOrder(symbol, orderId)`
- `GetOrderStatus(orderId)`
- `GetActiveOrders(wallet)`

**Критерии готовности:**
- Ордер отображается в интерфейсе биржи HyperLiquid
- В логах фиксируется реальный `MyOrderId` от биржи
- При Canceled трейдера — наш ордер отменяется через API

#### [P0-2] Безопасное хранение API ключей
**Задача:** Вынести API ключ/секрет из кода в конфигурацию (environment variables или secrets manager).

**Критерии готовности:**
- Ключи не присутствуют в репозитории
- Настраиваются через переменные окружения
- Документированы в `ENVIRONMENT_VARIABLES.md`

#### [P0-3] Установка leverage перед размещением ордера
**Задача:** Перед размещением копируемого ордера устанавливать leverage равный leverage трейдера.

**Критерии готовности:**
- Вызов API установки leverage до размещения ордера
- Логирование установленного leverage

### 6.2 P0.5 — Критично для безопасной эксплуатации и восстановления состояния

#### [P0.5-1] Персистентный `PositionMapping` и `OrderMapping`
**Задача:** Вынести маппинги позиций и ордеров из памяти в персистентное хранилище с восстановлением после рестарта.

**Требования:**
- хранить `PositionMapping` как source of record для связи позиций трейдера и пользователя
- хранить `OrderMapping` как связь `TraderOrderId -> MyOrderId` и статусы исполнения
- обеспечить atomic update маппинга и audit-записи при создании/изменении/закрытии

**Критерии готовности:**
- после рестарта маппинги восстанавливаются без ручного вмешательства
- `Decrease/Close/Filled/Cancel` используют восстановленные маппинги
- есть миграция схемы и тесты на восстановление state

#### [P0.5-2] Идемпотентность `NewOrders` и `NewTrades`
**Задача:** Гарантировать, что повторная доставка того же события не вызывает повторное копирование или повторную побочную обработку.

**Требования:**
- deduplication ключи для ордеров и трейдов
- окно хранения обработанных идентификаторов и защита от повторов после рестарта
- идемпотентность не только на уровне event intake, но и на уровне side effects

**Критерии готовности:**
- повтор одного и того же `OriginalOrder` не создаёт новый copy-order
- повтор одного и того же `OriginalTrade` не искажает snapshot позиции
- покрыто unit/integration тестами на duplicate delivery

#### [P0.5-3] Recovery after restart
**Задача:** При старте пересобирать in-memory state из биржи и персистентного хранилища.

**Поток восстановления:**
1. загрузить активные ордера трейдеров и пользователя с биржи
2. загрузить текущие snapshot позиций
3. загрузить незавершённые copy-order, mappings, dedup-state
4. пересобрать `FillsOrderService`, `CopyOrderStorageService`, snapshot и связи
5. выполнить первичную reconciliation-проверку и залогировать расхождения

**Критерии готовности:**
- после рестарта система продолжает сопровождать уже открытые позиции
- нет потери связи между `TraderOrder` и `MyOrder`
- startup recovery проходит автоматически и логирует результат

#### [P0.5-4] Dry-run / paper-trading режим
**Задача:** Добавить режим безопасного прогона реального потока событий без размещения ордеров на бирже.

**Требования:**
- отдельный feature flag
- полный проход decision pipeline
- фиксация виртуальных copy-order, причин решений и предполагаемых параметров ордера

**Критерии готовности:**
- при включенном режиме реальные API-вызовы размещения/отмены не выполняются
- UI и логи явно показывают, что система в dry-run
- можно анализировать те же решения, что были бы в production

#### [P0.5-5] Kill switch
**Задача:** Добавить глобальный механизм немедленного отключения исполнения копирования без остановки всей системы.

**Требования:**
- runtime flag из конфигурации или UI
- остановка новых execution-команд при сохранении мониторинга, подписок и snapshot
- логирование включения/выключения и причины

**Критерии готовности:**
- при активном kill switch новые copy-order не уходят на биржу
- intake событий, UI и диагностика продолжают работать
- состояние переключателя видно в логах и интерфейсе

### 6.3 P1 — Важно для надёжности

#### [P1-1] Миграция runtime-state в целевое персистентное хранилище
**Задача:** После внедрения персистентных mappings перевести runtime-state приложения с `SQLliteBD` на целевое server-grade хранилище.

**Область миграции:**
- `PositionMapping`
- `OrderMapping`
- deduplication state
- dead letter queue
- audit trail

**Критерии готовности:**
- runtime-state не зависит от файлового SQLite
- миграция выполняется без потери связей между позициями и ордерами
- есть сценарий rollback и проверки целостности после переноса

#### [P1-2] Исправление рекурсивного retry в WebSocket
**Задача:** Заменить рекурсивный retry на итеративный (while-loop с Task.Delay).

**Критерии готовности:**
- `OrdersTradesSubscriber` использует цикл вместо рекурсии
- Корректно ограничено число попыток или timeout

#### [P1-3] Обработка статуса Filled (проверка исполнения)
**Задача:** При `OrderStatus.Filled` у трейдера — проверить статус нашего ордера и выполнить fallback если наш ордер не исполнен.

**Алгоритм:**
1. Получить `MyOrderId` из маппинга
2. Запросить статус через `OrdersProvider.GetOrderStatus()`
3. Если наш ордер `Open` через N секунд — разместить рыночный ордер
4. Если `Canceled` — критическая ошибка, логировать + попытка синхронизации

**Критерии готовности:**
- Логируется расхождение статусов
- Есть fallback на рыночный ордер (configurable)

#### [P1-4] Reconciliation job
**Задача:** Реализовать периодическую сверку состояния между биржей, локальными snapshot, mappings и copy-orders.

**Области сверки:**
- открытые ордера трейдера ↔ локальные pending orders
- открытые ордера пользователя ↔ `OrderMapping`
- реальные позиции ↔ `PositionMapping`
- copy-order lifecycle ↔ фактические статусы на бирже

**Критерии готовности:**
- фоновая задача запускается по расписанию и при старте
- расхождения классифицируются по severity
- есть механизм сигнализации и, где безопасно, auto-heal/retry

#### [P1-5] Dead letter / failed actions queue
**Задача:** Все неудачные операции копирования и отмены складывать в отдельную очередь с возможностью безопасного повтора.

**Требования:**
- хранение payload, причины ошибки, числа попыток, последнего stack trace/response
- ручной и автоматический retry по политике
- защита от бесконечного повторения невалидной команды

**Критерии готовности:**
- неудачные `PlaceOrder` и `CancelOrder` не теряются
- по failed action видно, что, когда и почему упало
- retry не нарушает идемпотентность

#### [P1-6] Audit trail
**Задача:** Хранить полную причинно-следственную цепочку от сигнала трейдера до закрытия нашей позиции.

**Цепочка аудита:**
`TraderOrder -> CopyDecision -> MyOrder -> Fill -> Close/Cancel/Reconcile`

**Критерии готовности:**
- для любого copy-order можно восстановить входные данные, решение и результат исполнения
- audit trail доступен для расследования инцидентов
- audit записи пишутся и для dry-run, и для production режима

#### [P2-8] Обёртка над `DataBusEvents` / переход к интерфейсной шине
**Задача:** Уйти от прямого использования статического `DataBusEvents` в сторону `IEventBus` или совместимой обёртки.

**Критерии готовности:**
- публикация и подписка происходят через абстракцию
- тесты могут подменять шину без глобального состояния
- скрытые зависимости между сервисами сокращены

#### [P2-9] Удаление `async void` из event-цепочек
**Задача:** Заменить `async void` обработчики на управляемые async pipeline-методы с явной обработкой ошибок.

**Критерии готовности:**
- ошибки не теряются вне логирования
- можно дождаться завершения критичных этапов обработки
- порядок выполнения и retry контролируются явно

#### [P2-10] Разделение decision engine и execution engine
**Задача:** Жёстко разделить доменную логику принятия решения и внешнее исполнение на бирже.

**Критерии готовности:**
- decision layer не зависит от API HyperLiquid напрямую
- execution layer получает уже сформированную команду
- dry-run и тестирование decision logic возможны без моков биржи

#### [P2-11] Инфраструктурные абстракции для тестируемости
**Задача:** Добавить `IClock`, `IIdGenerator`, `IEventBus` и аналогичные abstractions для детерминированных тестов.

**Критерии готовности:**
- тесты не зависят от реального времени и глобального состояния
- уменьшается количество нестабильных integration-style unit tests
- новые сервисы не завязаны на `DateTime.UtcNow` и static-singleton инфраструктуру напрямую

## 7. Нефункциональные требования

### 7.1 Производительность
- Обработка события `NewOrders` должна завершаться до прихода следующего batch (обычно ~100ms между batch)
- Redis lookup < 5ms
- Размещение ордера на бирже — async, не блокирует поток обработки

### 7.2 Надёжность
- Автоматическое переподключение WebSocket при обрыве
- Автоматическая очистка памяти: порог 2000 ордеров → чистка до 500
- Логирование всех операций с ордерами (уровень INFO), ошибок (ERROR)
- Recovery after restart без ручного вмешательства
- Reconciliation должен выявлять расхождения до того, как они приводят к ошибочным сделкам
- Все execution-команды должны быть идемпотентны

### 7.3 Безопасность
- API ключи биржи — только в переменных окружения, не в коде
- `MyWallet` — не в публичном репозитории
- Наличие kill switch обязательно для production
- Dry-run режим должен исключать любое реальное размещение/отмену ордера

### 7.4 Правила кода
- Суффикс `Async` в именах методов **не используется** (правило проекта из WARP.md)
- Все сервисы — Singleton
- Async/await на всех операциях I/O
- Потокобезопасность через `ConcurrentDictionary` и `SemaphoreSlim`
